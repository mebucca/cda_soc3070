1. Contexto y objetivos

Este notebook retoma el ejemplo de bikers de la clase 14, con el código completo y paso a paso. Lo usamos en clase para reproducir en vivo cada decisión del análisis:

  1. por qué un criterio in-sample (AIC/BIC) no basta para diagnosticar overfitting;
  2. cómo se ve la curva training set vs. testing set cuando aumentamos la flexibilidad;
  3. por qué un solo split training set/testing set es una estimación ruidosa del error de generalización;
  4. cómo se construye un k-fold cross-validation: primero a mano en un fold, después automatizado con caret;
  5. cómo se compara el desempeño (y la estabilidad) de dos reglas de predicción con esos folds.

Los conceptos son los mismos que en las diapositivas; acá se muestra el código completo. Cada bloque corresponde a uno o más chunks ocultos en class_14.qmd.

3. Dos modelos

Fijamos dos especificaciones, igual que en las diapositivas, y las usamos en todo lo que sigue: dos objetos fit/predict con distinta flexibilidad.

Code 
simple_formula <- bikers ~
  temp + hum + workingday + factor(hr)

flexible_formula <- bikers ~
  poly(temp, 5, raw = TRUE) +
  poly(hum, 5, raw = TRUE) +
  factor(mnth) +
  factor(hr) * workingday +
  factor(weekday) +
  windspeed
  • simple_formula: efectos lineales de clima, un indicador de día laboral, y un efecto fijo por hora del día (24 categorías).
  • flexible_formula: polinomios de grado 5 en temperatura y humedad, efectos fijos por mes y día de la semana, una interacción hora × día-laboral, y velocidad del viento.

flexible_formula tiene muchos más parámetros. La pregunta de la sección 4 es: ¿eso la hace mejor?

6. ¿Qué tan estable es un solo split?

El “validation set approach” (un solo split) tiene un problema: el número que obtenemos depende de qué observaciones cayeron al azar en cada lado. Lo mostramos repitiendo el split 15 veces, con una complejidad fija (grado 8), y mirando cuánto se mueve el RMSE en el testing set.

Code 
rmse_testing <- numeric(15)
for (seed in 1:15) {
  set.seed(seed)
  split_id <- sample(seq_len(nrow(bikedata)), 600)
  train <- bikedata[split_id[1:300], ]
  test <- bikedata[split_id[301:600], ]
  model <- lm(bikers ~ poly(temp, 8, raw = TRUE), data = train)
  rmse_testing[seed] <- rmse(test$bikers, predict(model, newdata = test))
}

7. k-fold cross-validation, paso a paso

7.1 Construir los folds

Los datos tienen 24 horas dentro de cada día. Si repartimos horas al azar entre folds, el training set de un fold puede contener otras horas del mismo día que estamos evaluando. Esto sobreestima el desempeño si el objetivo es predecir días completos nuevos. Por eso agrupamos por day.

group_vfold_cv(data, group, v) (de rsample) arma v folds agrupando por la variable group: ningún grupo —acá, ningún día— queda repartido entre el training set y el testing set del mismo fold. Devuelve un objeto folds con una columna splits (una lista donde cada elemento es un split: un objeto que guarda qué filas de data van a training y cuáles a testing en ese fold) y una columna id con el nombre de cada fold.

Para sacarle los datos a un split hay dos funciones: analysis(split) devuelve el training set de ese fold, y assessment(split) devuelve el testing set.

Code 
set.seed(3070)

7.3 Automatizar con caret

Repetir el ajuste a mano en cada fold funciona, pero caret hace exactamente eso con dos comandos: trainControl() para decirle cómo evaluar, y train() para ajustar y evaluar en un solo paso. Reusamos los mismos folds que construimos en 7.1 — no hace falta generar otros.

Code 
train_indices <- lapply(folds$splits, function(s) s$in_id)
length(train_indices)
[1] 10
Code 
length(train_indices[[1]])  # observaciones en el training set del fold 1
[1] 7766

lapply(lista, función) aplica esa función a cada elemento de la lista y devuelve una lista nueva; acá la aplicamos a cada split de folds$splits. split$in_id es el vector de filas que rsample asignó al training set de ese fold — lo mismo que devuelve analysis(), pero como índices en vez de datos. caret necesita justo eso: una lista con los índices de entrenamiento de cada fold.

Code 
ctrl <- trainControl(method = "cv", index = train_indices, savePredictions = "final")
  • method = "cv": evaluar con cross-validation (el default de caret es bootstrap).
  • index = train_indices: usar nuestros folds —agrupados por día— en vez de que caret arme folds aleatorios por su cuenta.
  • savePredictions = "final": guardar la predicción fuera de muestra de cada caso, por si después queremos inspeccionarlas.
Code 
candidate_models <- list(Simple = simple_formula, Flexible = flexible_formula)

cv_models <- list()
for (model_name in names(candidate_models)) {
  cv_models[[model_name]] <- train(
    candidate_models[[model_name]],
    data = bikedata,
    method = "lm",
    trControl = ctrl
  )
}

train() es el comando central de caret: toma una fórmula, un data, un method (qué algoritmo ajustar — acá "lm", pero con la misma sintaxis podría ser un árbol o un random forest) y un trControl (cómo evaluar). Para cada fold en ctrl$index, ajusta lm(formula, data = training de ese fold) y lo evalúa en el resto. El loop repite esto una vez por fórmula.

Una diferencia con lo que hicimos a mano: $resample solo trae el error en el testing set de cada fold. caret no guarda el ajuste de cada fold por separado, así que no hay forma directa de recuperar el error en el training set de cada uno. 8. Fugas de información y el test final

Reglas que hay que respetar para que todo lo anterior siga siendo válido:

  • estandarizar, imputar o seleccionar predictores dentro de cada fold, nunca con todo el dataset;
  • no repartir observaciones relacionadas (como horas del mismo día) entre training set y testing set; por eso usamos group_vfold_cv(group = day);
  • si usamos CV para elegir entre simple_formula y flexible_formula (o para afinar cualquier hiperparámetro), esos folds pasan a ser parte del entrenamiento del procedimiento completo: ya no sirven como estimación independiente del error final.

  1. proponga una tercera regla de predicción (puede ser una variante de flexible_formula);
  2. ajústela con train(tercera_formula, data = bikedata, method = "lm", trControl = ctrl);
  3. compare su $results con los de cv_models$Simple y cv_models$Flexible;
  4. identifique una posible fuga de información si alguien construyera esa regla de otra forma;
  5. explique cómo cambiaría la construcción de los folds si el objetivo fuera predecir el mes siguiente en vez de días dentro del mismo período.
